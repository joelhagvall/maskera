# Training data protection

This document defines the privacy gate for the privacy-clean
`maskera-sv-ner` release line. A model belongs to that line only when its
published files include a valid `privacy-attestation.json`; a model without
that file is a legacy artifact and must not be reused, exported, or published.

## What the attestation covers

Maskera's task-specific fine-tuning and distillation data is generated by
`training/generate_data.mjs`. It does not include customer data, logs, forum
posts, news corpora, scraped text, public NER corpora, or model-generated
pseudo-labels from those sources.

The generator constructs Swedish NER examples from templates and gazetteer
fragments. Names, place names, and organisation names are class exemplars; the
sentences are random combinations, not collected records or claims about the
named people or organisations. No sourced account, contact, identity, or
device identifier is attached to them. Every generated address contains an
explicit synthetic marker such as `Maskera`, `Provdata`, `Fiktiv` or
`Testkorpus`; an ordinary street name is rejected even without a postal code,
because a random house number could still resolve to a real property. Because
ordinary names can coincide by chance, the accurate guarantee is source
isolation, no sourced relationships, marked addresses, and identifier
exclusion—not that no generated name pair could ever match a living person.

The privacy-clean release runner uses synthetic evaluation data and non-record
category probes. Historical benchmark reports may retain aggregate results and
source names from earlier public corpora, but their raw text is not a release
input and is not kept in the checkout. An optional external evaluation must be
acquired separately, logged aggregate-only, and deleted after measurement.

Every generated row is rejected if it contains any of these categories:

- IBAN or another account-shaped string;
- personal, co-ordination, or organisation number;
- phone number, e-mail address, account handle, URL, or public IP address;
- bankgiro, plusgiro, OCR, BIC/SWIFT, wallet address, card/account-like long
  number, or another numeric payment identifier;
- UUID/record identifier, MAC/device identifier, or Swedish vehicle
  registration;
- postal code, because it can make a generic street mention more precise.

This prohibition also applies to officially reserved test values. Those
values remain useful in `@maskera/core` detector tests, but the NER model does
not need them and they do not enter its weights.

## Fail-closed chain

1. The generator writes the exact train/validation row counts and SHA-256
   hashes to `data/source-manifest.json`, together with the generator's own
   SHA-256.
2. `privacy_guard.mjs` scans every token without returning or printing the
   matched value. It also requires an explicit synthetic marker in every ADR
   span. Diagnostics expose only the prohibited category.
3. `privacy_attestation.mjs` requires the JSONL files to match the source
   manifest byte-for-byte and requires the generator code to match its hash.
   It records the source-manifest hash, every provenance/audit script hash, and
   the exact KB-BERT Hub revision in `privacy-attestation.json`.
4. Training, continued training, vocabulary trimming, distillation, ONNX
   export, quantisation, and publication all require and validate that
   attestation. Appending a converter output or manually editing a row
   invalidates the manifest.
5. Vocabulary trimming prioritises pieces by frequency in the exact attested
   synthetic splits. If fewer than 20,000 pieces occur there, it fills the
   remaining capacity deterministically from the pinned KB-BERT tokenizer's
   native id order. It never reads evaluation or public text for selection.
6. The publication script stages only tokenizer/configuration files, the three
   ONNX weight variants, the model card, `NOTICE`, and the attestation. Raw
   training rows are never included in the model repository or npm package.

Run the local gates from `training/`:

```bash
BALANCED_REPLAY_TRAIN_ROWS=1200 BALANCED_REPLAY_VAL_ROWS=200 \
HARD_NEGATIVE_TRAIN_ROWS=2800 HARD_NEGATIVE_VAL_ROWS=560 \
  node generate_data.mjs 60000 4000
node audit_data.mjs
node privacy_attestation.mjs
node verify_attestation.mjs data/privacy-attestation.json
node --test privacy_guard.test.mjs privacy_attestation.test.mjs
```

The published 2026-08-06 v19 artifact therefore contains 64,000 training
rows and 4,760 disjoint validation rows. Its train, validation, and generator
SHA-256 values are recorded in `docs/BENCHMARKS.md` and bound in the artifact's
schema-2 attestation. The published weights carry that attestation unchanged.

## Base-model boundary

The attestation covers Maskera's task-specific data. It does not claim that
the third-party KB-BERT base checkpoint was pretrained on synthetic-only data.
KB-BERT was published by the National Library of Sweden under CC0, but a
copyright licence is not a GDPR determination and does not waive rights held
by other people. Creative Commons itself notes that CC0 does not affect third
parties' privacy or publicity rights.

For that reason the accurate statement is: **the privacy-clean Maskera v19
release adds no sourced real records, plausible real street/number pairs, or
structured identifiers during fine-tuning or distillation.** An absolute
claim about all information ever seen during KB-BERT pretraining would require
replacing KB-BERT with a model and tokenizer pretrained from scratch on a
separately audited corpus.

The distinction follows the European Data Protection Board's position that
whether a trained model is anonymous must be assessed case by case, including
whether people can be identified or training data extracted from it. The
token-classification model emits labels and spans rather than generating text,
which reduces extraction risk but does not turn a licence into a privacy
guarantee.

Sweden's data-protection authority, IMY, likewise describes synthetic training
data as risk-reducing while stressing that creating it from real personal data
is itself processing subject to the GDPR. Maskera's task generator does not
transform source records: it constructs rows directly from templates and
gazetteer fragments. That distinction does not remove the separate KB-BERT
boundary above.

## Legacy-artifact rule

The v18 training journal records earlier experiments with public news, blog,
encyclopedic, chat, and forum corpora. Aggregate history and source names stay
in the repository for auditability, but raw rows, downloads, pseudo-labels and
logs are not valid inputs to the privacy-clean release line and have been
removed from the active checkout. Legacy weights may still exist in ignored
research or currently published demo caches; their missing or mismatched
attestation makes the verifier and publication script reject them. A privacy
reset therefore starts again from the CC0
KB-BERT base checkpoint, creates new synthetic-only data, and produces a new
teacher, student, tokenizer trim, and ONNX export. Documentation and benchmark
snapshots must not describe that candidate as published until all quality gates
pass and the pinned release artifacts have actually changed.
